# Design notes

## Shape

Six modules, one direction of dependency:

```
warehouse.py  -> sqlite star schema, seeded, generated by code
guard.py      -> guarded text-to-SQL (static checks + sqlite authorizer + limits)
tools.py      -> five pydantic-typed tools; sql_query is the only open one
providers.py  -> LLMProvider protocol; StubProvider default, Anthropic/OpenAI lazy
agent.py      -> plan -> call -> observe -> respond, with a step budget and a trace
evals.py      -> golden set, three graders, attack suite, scorecard
```

Nothing above `providers.py` knows which model is answering, and nothing below
`tools.py` knows a model exists. That separation is what makes the eval harness
meaningful: a run with the stub and a run with a hosted model exercise the same
tools, the same guard and the same graders.

## Why the guard is not a regex

The common text-to-SQL guard is a keyword denylist, and it fails the moment the
model writes something the regex did not anticipate: a CTE that wraps a write, a
comment that hides a second clause, a `UNION` onto a table the prompt never
mentioned. The load-bearing layer here is `sqlite3.set_authorizer`, which runs
inside the parser and is consulted for every table, column and function the
prepared statement touches. It sees what the engine sees. The static checks in
front of it (single statement, `SELECT`/`WITH` only, no comment tokens) exist to
produce a readable refusal rather than a generic authorization error, not because
they are trusted. The allowlist is a schema, not a blocklist: a table absent from
`ALLOWED_SCHEMA` is invisible, which is why `internal_credentials` exists in the
database and is unreadable through the tools.

`LIMIT` injection and the cursor row cap are a separate concern. They are not
security - they stop a well-formed query returning 400,000 rows into a context
window.

## Why the eval has two arms

A single-arm scorecard on the exact phrasings you wrote your router against
measures nothing. The paraphrase arm restates all 25 intents - same expected
answer, same expected tool trajectory - and the gap between the arms is the
result worth reporting: 1.00 against 0.48 for the rule-based stub. The failure
mode it exposes is the one that hurts in operation: the copilot does not answer
wrongly, it silently drops to a clarifying question and the planner concludes it
is useless.

Three graders, deliberately shallow. Exact/contains for refusals and clarifying
questions, numeric with a relative tolerance for anything with a number, and a
trajectory match on the tool sequence. Tool-selection accuracy is reported
separately from answer pass rate because they fail independently: right tool with
a wrong filter, or right answer reached by an expensive detour, are different
problems with different fixes.

Ground truth for numeric items is a SQL statement executed directly against the
warehouse, outside the tool layer. If a tool's arithmetic drifts, the eval fails
rather than agreeing with itself.

## Known weaknesses

The numeric grader keys off an `Answer:` marker the stub always emits; a hosted
model needs a structured output contract or a looser parser, and the looser
parser is how graders start passing things they should not. Step counts include
the final response turn, so a one-tool question reports two steps. The what-if
tool is deterministic arithmetic on an average lead time, not a distributional
model - it answers "how exposed am I", not "what is the service level".
